Reproduction and case-level values: [phase diagnostic](artifacts/libero_action_value_gate_egl_unseen_task_v1_20260925/N50_PHASE_GUIDANCE_DIAGNOSTIC.md), [machine-readable result](artifacts/libero_action_value_gate_egl_unseen_task_v1_20260925/N50_PHASE_GUIDANCE_DIAGNOSTIC.json), [analysis script](research/semantic_token_cd/analyze_n50_phase_guidance.py).

## Action-dimension transfer diagnostic (2026-09-25)

I decomposed the same clean-top-1/top-2 guidance score by each of the first six action dimensions, using episode medians in the SIMPLER four-Google-task seed-100–199 discordant subset and three separate LIBERO cohorts. SIMPLER has 101 Rescue/28 Harm; its Rescue-higher AUC is below .5 for **all six** dimensions (range .304–.429). In LIBERO, the fresh EGL N=40 and held-out OSMesa N=40 have Rescue-higher AUC above .5 for five of six dimensions; the unseen-task EGL N=50 has five above .5 and one .3. Cohorts remain separate.

This weakens the simple explanation that the transfer contrast is caused by one anomalous action coordinate. It is consistent with a broader change in how the same counterfactual margin relates to successful episodes, but it is still observational: sample sizes for LIBERO Rescue/Harm are small, and checkpoint, task family, renderer, and state distribution are not jointly controlled. The N=50 positive-G execution gate remains neutral, so episode-level association does not establish that applying guidance when G is positive causes success. Do not turn these dimension AUCs into a dimension gate.

**Hypothesis update:** a single action dimension is unlikely to explain the SIMPLER/LIBERO direction difference. **Decision: REFINE.** The next causal discriminator must control policy checkpoint and vary benchmark/task environment, or otherwise obtain same-state action-value interventions with physical task feedback; current cohorts cannot separate those factors. Full per-episode results: [cross-benchmark dimension report](artifacts/cross_benchmark_dimwise_action_value_v1/CROSS_BENCHMARK_DIMWISE_ACTION_VALUE.md), [machine-readable data](artifacts/cross_benchmark_dimwise_action_value_v1/CROSS_BENCHMARK_DIMWISE_ACTION_VALUE.json), and [reproducer](research/semantic_token_cd/analyze_cross_benchmark_dimwise_action_value.py).

A device-policy issue was discovered during incident review. The old launcher restricted CUDA visibility to GPUs 1, 2, 3, 6, and 7, but passed the same numeric ID to `MUJOCO_EGL_DEVICE_ID`. A no-context EGL enumeration mapped EGL ordinals as `0→GPU3`, `1→GPU2`, `2→GPU0`, `3→GPU1`, `4→GPU7`, `5→GPU6`, `6→GPU4`, `7→GPU5`. Thus the old GPU2 renderer assignment could select physical GPU0, and renderer IDs 6/7 selected prohibited physical GPU4/5. The earlier statement that GPUs4/5 were untouched was wrong; details are in [DEVICE_MAPPING_INCIDENT.md](/home/leju-suzhou/zjt_ws/token-cd/artifacts/libero_action_value_trace_pilot_v2/DEVICE_MAPPING_INCIDENT.md).

The launcher/worker were patched to enumerate EGL DRM render nodes, resolve the intended physical GPU by PCI BDF, fail closed on ambiguous/missing mappings, restrict CUDA visibility to the model GPU, and set MuJoCo's EGL ordinal only after robosuite's import-time guard. The mapping fix was verified without creating a GL context. A subsequent single technical validation requested physical GPU1 and correctly resolved to EGL ordinal3 / PCI `0000:21:00.0`; NVML showed model memory only on physical GPU1. That run nevertheless emitted repeated Xid 31 on GPU1. Its traceback reached MuJoCo `mjr_readPixels` during camera observation readback. The worker was stopped immediately. Therefore wrong-card selection explains the GPU4/5 incidents, while the remaining Xid is an independent MuJoCo EGL/driver/render-readback fault not yet fixed. At the time of this initial report, no discoverable `libOSMesa` runtime was available; a private runtime was later extracted and validated below.

That initial EGL stop was technical/data-fidelity related, not a method failure. The later OSMesa pilot is exploratory and does not update historical EGL method-effect estimates.
